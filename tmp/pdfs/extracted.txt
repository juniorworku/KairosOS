Product description
  Visual revision 1.1: use white/light gray, deep charcoal and one vibrant deep-purple accent. Earlier multi-
  color pastel guidance is superseded.




Purpose
Help founders, solopreneurs, freelancers, and team leads turn priorities into realistic scheduled work while
keeping administrative commitments moving. Initial design serves one person's workspace; shared team
planning is deferred.

Users currently carry goals, tasks, meetings, replies, and promises across disconnected tools. Kairos joins those
contexts so the user can decide what matters, protect time, and follow through without managing a complex
dashboard.


Product promise
Set the direction. Approve a realistic plan. Focus on the work. Kairos keeps track and brings useful follow-ups
and proposed adjustments back for review.


Four pillars
• Goal and season planning: define outcomes, milestones, next actions, constraints, and follow-up loops.

• Calendar and capacity: propose time blocks around real commitments and expose tradeoffs when work does
  not fit.

• Focus and flow: a dedicated work view, distraction controls, optional lo-fi audio, and a floating session timer.

• Coaching and accountability: daily priority alignment, evidence-based follow-ups, weekly reflection, and
  specific proposed fixes.


Product model
A season is an optional longer planning container. A goal has an outcome and success measure. A plan links
milestones, tasks, time allocations, and follow-up loops to that outcome. A support area holds ongoing
responsibilities without requiring an artificial goal. A calendar block reserves time; a focus session records effort.
Completion and outcome progress require their own evidence.

Planning horizons: one day, one week, two weeks, four weeks, six weeks, and twelve weeks. Longer plans are
reviewed over time; the assistant must not fill every future hour by default.

A loop is a recurring or event-triggered instruction with a purpose, scope, schedule, evidence sources, allowed
actions, output, and stopping condition. Goal loops advance outcomes; standing loops cover daily administration.

Scope boundaries
The product vision includes email follow-through, meeting context, broader calendar integrations, and AI handoff.
These are staged capabilities, not claims of current availability. Native meeting capture and cross-device
blocking require separately supported device software. Initial work retains the existing stack and personal-
account model.

Avoid a new page for each routine, mandatory chat for simple actions, unexplained scores, fabricated progress,
and automatic rescheduling. Use original Kairos text and identity while following the reference's layout and
interaction simplicity.


Outcome measures — proposed, targets pending baseline
Track onboarding-to-first-approved-plan completion, time to first useful daily plan, weekly coach-sync use,
commitment closure, goal outcome check-ins, focus session completion, proposal acceptance/edit/rejection, and
notification dismissals. Distinguish scheduled minutes, recorded effort, completed tasks, and measured
outcomes. Collect only consented telemetry; measure against a baseline before setting improvement targets.

Approval contract
Reading within granted scope, analyzing, drafting and reporting can run automatically. Inferred commitments
remain suggestions until accepted. Every assistant-proposed scheduling adjustment needs approval, including
moving its own focus blocks. Approving a local plan does not implicitly authorize external publication: the review
must explicitly name the destination and effects. Direct user edits are explicit actions; clearly identify remote
effects before saving. Messages, invitations and destructive external changes require explicit authorization. A
batch approval names every included change.

End-to-end workflows
1. Clarify and activate a plan — R01, R02, R10
  1. User chooses a horizon and describes a goal, task or plan.

  2. Coach asks targeted questions about success, priority, current progress, capacity, deadline, obstacles and
  dependencies. User can skip optional context.

  3. With consent, existing calendar availability informs capacity. Manual availability remains possible.

  4. Kairos proposes milestones, concrete tasks, estimates, suggested blocks and follow-up loops. It exposes
  capacity shortfalls and assumptions.

  5. User edits, accepts or rejects items. Approved items become the active plan; external publication is explicitly
  selected and approved.

  6. Home opens the calendar with the approved work and visible remaining decisions.

An incomplete conversation saves a draft. No available slots produces options to reduce scope, change dates or
change capacity, rather than an invented schedule.


2. Daily coach sync — R05, R06
  1. User opens home; right panel offers today's sync and a concise brief.

  2. Coach brings priorities, upcoming meetings, urgent commitments, unfinished work, and relevant changes
  with source freshness.

  3. User confirms today's energy, available time and core focus; can correct priorities.

  4. Coach proposes a feasible day with focus blocks, admin time and buffers, explaining tradeoffs.

  5. User accepts individual changes or the listed batch. Unapproved changes remain previews.

  6. Next focus task has a clear Start focus action.

Skipping sync preserves the existing plan. New urgent information generates another proposal, never an
automatic adjustment.


3. Focus — R07–R09, N02
  1. Start from a task or calendar block; confirm intended duration and session objective.

  2. Apply configured supported distraction rules and optionally start lo-fi/ambient audio with playback and
  volume controls.

  3. Dedicated focus view shows the task and only essential controls. Floating timer stays accessible when
  navigating elsewhere in Kairos.

  4. Pause/resume/end updates session state and device controls consistently. Timer derives from persisted
  timestamps, not browser animation ticks.




KAIROS / PRODUCT BLUEPRINT                                                                                         8
  5. On end, release blocking and ask what was accomplished, what remains, and whether the task is complete.
  Optional self-rating is labeled as such.

  6. A blocker or unfinished work can generate a proposed next action or replacement block.

Audio failure does not block work. Permission/device failure shows which controls are unavailable. Sleep, reload,
disconnection and duplicate endings must not duplicate time or strand blocking. P0 pause default: suspend
session blocking; explain this in controls.


4. Follow-up and schedule rescue — R06, R10, R14
A scheduled or event-triggered loop reads permitted evidence, reconciles known commitments, checks its
conditions and produces a report, draft or proposal. For example: a meeting overlaps accepted focus time;
Kairos proposes a replacement slot with the original and replacement visible. Until approved, the original
remains unchanged. If the replacement becomes unavailable before approval, require a refreshed proposal.

User may accept, edit, dismiss, snooze or pause the loop. Snoozing changes notification timing, not a task's due
date. Delivery of a reminder never closes a commitment.


5. Meeting lifecycle — R13, R14
Before: assemble available history, open threads, promises and meeting objective. During: use supplied notes
initially; native audio capture is staged separately. After: extract decisions and candidate commitments, identify
owners/dates and prepare a follow-up. User reviews uncertain facts and accepts tasks/drafts. Link to original
evidence; merge duplicates with existing work. Waiting items remain open until answered, cancelled or
deliberately closed.


6. Weekly review — R11, R16
Show intended versus actual effort, completed tasks, outcome check-ins, waiting items and repeatedly moved
work. Ask what changed and what to carry forward. Coach proposes specific scope or calendar changes for the
next week. User approves changes. Friday wrap and week-ahead prep use the same review history to avoid
conflicting summaries.


State rules
• Plan: draft → proposed → active → completed/archived; revisions preserve the prior accepted version until
  approved.

• Commitment: suggested → accepted → ready/in progress/waiting → completed; dismissal and cancellation
  are separate terminal outcomes. Scheduling is an independent attribute.

• Proposal: pending → applied/dismissed/expired/conflicted; editing creates a new reviewable version.
  Repeated acceptance cannot apply twice.

• Focus: idle → running ↔ paused → ended; exact time accounting survives reload and retry.

• Loop: draft → active ↔ paused → stopped. Individual runs retain success/partial/failed/skipped evidence.

Interface architecture
  Visual revision 1.1: use white/light gray, deep charcoal and one vibrant deep-purple accent. Earlier multi-
  color pastel guidance is superseded.




Home workspace — R03
Calendar-first and minimal, following the supplied Superfocus screenshots. White background, light grey
dividers, neutral event fills, a single purple accent, rounded corners and restrained icons. Use original Kairos
wording and assets. This is the target design; current warm/lavender styling is implementation history.

Desktop with coach closed: left goals/tasks panel approximately 26%, calendar approximately 74%. Use
practical min/max widths rather than a rigid ratio on every viewport. Coach open: a resizable or fixed-width right
panel uses part of the remaining workspace; preserve a usable calendar and offer collapse. On medium screens
use an overlay drawer; on phones use a day/agenda surface with task and coach sheets. Breakpoints and final
dimensions require prototype validation.


Left panel
Small Tasks heading, quick add and filter controls. Expandable season/goal rows reveal milestones and tasks in
place. Separate support areas include Inbox, Life Admin, Relationships and Family, with user-defined areas
supported. Selecting a goal filters/highlights its calendar work; offer a visible clear-filter action. Drag a task onto a
slot to create a linked time reservation; provide Schedule as a non-drag equivalent. A task can have multiple
sessions without becoming duplicate tasks.


Calendar canvas
Compact previous/next, Today/This week, date range, Day/Week switch, calendar filters and sync status. Include
an all-day row, hourly grid, current-time marker and clearly visible working hours. Events show title and time as
space permits; source/status appear through labels/icons and details.

Click an empty slot to create; drag to move; resize duration. Event popover contains title, date/time, duration,
goal/task link, recurrence, notes, source and available actions. Expand details only when needed. Do not expose
provider IDs or internal job mechanics in normal flows.

Use consistent neutral goal/area treatments and purple emphasis, supplemented by source/status indicators.
Proposed additions use dashed outlines; moves show source/destination; removals show a clear proposed-
removal treatment. A compact review strip summarizes added/moved/removed counts and opens the detailed
review. Accepted and proposed items must remain distinguishable without color.


Coach panel
One contextual panel for daily sync, chat, recommendations, follow-ups and approvals. Default content
emphasizes today's core priorities and next decision, not a feed of metrics. Each actionable card includes
reason, evidence/source, concrete change and accept/edit/dismiss controls. Full chat can clarify a proposal;



KAIROS / PRODUCT BLUEPRINT                                                                                             10
conversation alone does not approve a vague future change. Users can revisit pending approvals.

Email and meeting administration appears as concise actionable cards here; supporting details open on
demand. Routine reports should be bundled; urgent notifications follow user preferences.


Focus mode
Dedicated workstation emphasizes task, session objective, time and pause/end. Optional audio has user-
controlled playback/volume. Configured blocking shows per-device actual status. Floating in-app timer is
draggable, minimizable, keyboard accessible and cannot hide essential controls offscreen. Cross-app system
floating behavior needs platform capability validation; do not promise it from a normal browser tab.

At session end use a short completion sheet: accomplishment, task state, optional outcome check-in/self-rating
and next step. Recorded time and user-reported progress have separate labels.


Component and state inventory
Goal tree, task row, quick capture, calendar event/popover, proposal card/review strip, coach conversation, loop
settings, focus workstation/timer, session completion sheet and weekly review. Each requires loading, empty,
error and relevant stale/offline/permission-denied states. Empty state guides creation without seeded fictional
commitments. Keyboard focus returns to the initiating control after dialogs; respect reduced motion and text
zoom. Final fonts, tokens and minimum text sizes are validated in prototype review, not copied blindly from tiny
screenshot text.

Screen design & components
Design revision: 1.1 / 30 October 2026. The requested Clean Tech direction supersedes the earlier pastel
category palette. Product behavior and approval requirements remain unchanged. Dimensions below are
proposed design targets to validate in a prototype.


1. Visual system
White #FFFFFF surfaces; light gray #F6F7F9 canvas; charcoal #17191F primary text; slate #596170 secondary
text; subtle #E2E5EB borders. Deep purple #6438E8 is the sole vibrant accent for primary actions, selected
controls, links and focus indicators. Pale purple #F0EBFF is a tint of that same accent. Use neutral labels and
outlines for event categories, not additional hues. Success, warning and error states use explicit text and icons
so meaning never depends on color.

Use a clean sans-serif typeface, 32-40 px major headings, 20-24 px screen headings, 14-16 px body and 12-13
px supporting metadata. Minimum sizes and contrast require device verification. Use an 8 px spacing rhythm
with 4 px fine adjustments; 16-24 px panel padding, 8 px event corners and 12 px panel corners. Borders supply
separation; shadows are reserved for floating surfaces. One primary action per decision context.


2. Screen S01 / Welcome and context
Purpose: establish the user's intent without forcing a long setup interview.

Layout: slim brand header, centered content column, progress indicator and a visible Save and exit action.
Present two starting choices: plan a goal, or organize existing work. Explain what the assistant will prepare.
Optional account connection follows; manual availability is available.

Steps: choose intent; select planning horizon; describe the desired outcome; connect sources or continue
manually. Next advances only after required information is supplied. Retain entries when navigating back.
Connection denial explains what remains usable.

Components: intent cards, horizon selector, text field, source connector, progress stepper, inline validation and
primary Continue button.


3. Screen S02 / Goal clarification
Purpose: turn a broad ambition into an actionable brief.

Layout: structured goal form with a compact conversational follow-up area. Show known answers as editable
fields, not buried only in a transcript. Ask for success measure, current position, deadline, available time, priority,
constraints and dependencies. Distinguish required answers from optional coaching context.

Steps: capture goal; ask the most relevant unanswered question; summarize assumptions; let user correct;
generate the proposed plan. Do not require every possible question for a simple one-day task. AI unavailable
state offers a manual goal and task form.

Components: outcome fields, date picker, capacity input, editable answer chips, question card, draft-save status
and Generate plan action.

4. Screen S03 / Plan review and activation
Purpose: make the assistant's proposal concrete and reviewable.

Layout: outcome summary above milestone/task list; calendar preview alongside on wide screens; proposed
loops below. Each item shows purpose, estimate, date or frequency, and assumptions. A capacity summary
explains unused time or overcommitment.

Steps: inspect the plan; expand supporting reasons; edit tasks or timing; choose proposed items; review listed
effects; approve. External publication names the calendar destination and effects explicitly. Keep local
acceptance and remote publication distinct unless a single approval explicitly includes both.

No capacity: offer reduce scope, extend deadline or change availability. Rejected suggestions leave accepted
work intact. Changed availability invalidates affected suggestions and asks for renewed review.

Components: milestone list, task editor, capacity summary, calendar preview, loop settings card and approval
summary.


5. Screen S04 / Calendar home
Purpose: manage priorities and real-world time in one workspace.

Desktop: goals/tasks on the left, calendar in the center and collapsible coach on the right. With coach closed,
use approximately 26% / 74%; constrain sidebar to a usable range. At 1440 px, an illustrative open layout is 280
px sidebar, 800 px calendar and 320 px coach, with the remainder used by dividers/padding. This is a prototype
target, not a fixed rule.

Left: quick capture; expandable season goals with tasks; support areas; calendar/source filters. Center: date
navigation, Day/Week, all-day row, hourly grid, current-time marker, source freshness and proposal strip. Right:
today's sync, pending decisions, follow-ups and contextual chat.

Steps: expand a goal; drag a task into time or use Schedule; inspect event; edit through popover; start focus.
Dragging assistant-proposed changes does not bypass proposal review. Direct user edits identify any external
save effects. Clicking a blank slot creates an explicit task/event/block choice.

Five- or seven-day display is a user preference; default seven-day week follows the reference. Work-hour display
can be expanded. Source labels distinguish Google events, local events and goal blocks without a category
rainbow.


6. Screen S05 / Daily coach sync
Purpose: agree on today's core work before focus.

Panel structure: concise daily brief; today's constraints; proposed top priorities; proposed time blocks; pending
decisions; chat input. Start with actual goals and available time. Ask about changed capacity and blockers.
Explain priority tradeoffs briefly, with evidence links available on demand.

Steps: review brief; correct priorities; tell coach today's capacity; inspect proposed day; approve individual
changes or the enumerated batch; start selected task. Skipping sync preserves the existing plan. The assistant
does not interpret a conversational acknowledgment as blanket authorization for unspecified changes.

Components: brief card, priority list, capacity prompt, proposal cards, evidence disclosure and Start focus action.

7. Screen S06 / Proposal review
Purpose: approve every assistant-proposed schedule adjustment.

Layout: compact summary strip in calendar; detailed drawer for review. Each change shows action type, previous
state, proposed state, reason, affected task, source and destination. Additions use a dashed outline; moves
show old/new positions with labels; removals remain visible until approved.

Steps: select a proposal; inspect before/after; edit or dismiss; approve; revalidate current calendar; apply; report
local and external outcomes separately. A stale proposal shows the conflict and offers a refreshed version.
Failure must preserve accepted state or explain any partial effects.

Components: change card, before/after comparison, selection checkbox, destination summary, Apply selected,
conflict banner and retry/reconcile action. Repeated approval is idempotent.


8. Screen S07 / Focus workstation and floating timer
Purpose: protect attention while keeping essential controls accessible.

Workstation: task title and intended outcome, timer, pause/end controls, device protection status and optional
audio. Hide nonessential calendar and chat content during focus, while allowing intentional return to planning.
Starting a session uses only configured supported blocking rules.

Floating timer: compact neutral surface with purple active indicator, task label, elapsed/remaining time and
pause/end. Drag handle, minimize and keyboard move controls; restore a safe position on viewport change. The
first scope is in-app floating. A timer above other applications is a separate platform decision.

Steps: select task; confirm duration/objective; start; verify per-device blocking status; optionally play audio;
pause/resume; finish. Proposed pause behavior releases blocking while paused. Show unavailable controls
honestly. Emergency unblock works even when the server cannot be reached; timed rules expire independently.

Audio controls: play/pause, volume, track/source and mute. No automatic sound before a user gesture. Audio
failure leaves the timer usable. Licensing/source selection remains a delivery decision.


9. Screen S08 / Session completion
Purpose: record evidence and choose a useful next step.

Layout: short completion sheet with actual recorded duration; accomplishment prompt; explicit task status;
optional outcome measure and optional self-rating. Do not infer task completion from timer expiry. Do not show a
precise focus score without defined observation inputs and validation.

Steps: describe result; mark task complete or unfinished; record measurable progress if applicable; capture
blocker; save. Offer a proposed continuation session or return to calendar. Saving session evidence does not
approve a new calendar adjustment.

Components: duration summary, status control, note field, measure input, optional rating and next-step proposal.


10. Screen S09 / Follow-ups and loop settings
Purpose: let the user understand and control ongoing assistant work.




KAIROS / PRODUCT BLUEPRINT                                                                                         14
Follow-ups are coach-panel cards grouped by urgency and routine. Expand to inspect evidence, task owner, due
date, draft and proposed action. Email sending and external changes require explicit authorization. Dismiss
hides a finding; snooze changes reminder time; neither means the underlying commitment is complete.

Loop detail contains purpose, goal/area scope, schedule, timezone, permitted sources, criteria, quiet hours,

11. Screen S10 / Weekly review
Purpose: learn from the week and prepare a realistic next one.

Layout: outcome progress, completed work, scheduled versus recorded effort, repeatedly moved work,
unresolved commitments and short reflection prompts. Focus time and goal outcomes remain separate. Place
proposed next-week adjustments beside a calendar preview rather than burying them in prose.

Steps: inspect evidence; correct missing progress; decide carry-forward/drop/defer; discuss constraints;
generate next-week proposal; approve exact changes. Defer changes a commitment deliberately; it is not silent
rollover.

Components: outcome summary, effort comparison, carry-forward list, reflection form and next-week proposal
review.

13. Responsive and accessibility behavior
Desktop keeps the calendar dominant. Tablet uses a coach drawer over the workspace. Phone defaults to

Features & integrations
Follow-up library
Cadences below come from the user's requested workflow inventory; all are configurable in the user's timezone.

Implementation blueprint
Status: proposed technical plan. This document authorizes no code execution, integration connection or
deployment.


Existing foundation and gap
The repository documents React/Vite/TypeScript, FullCalendar, FastAPI/Pydantic, PostgreSQL, Celery/Redis,
goals, tasks, local recurrence, planning proposals, Google Calendar consent, focus logs, coaching, a Chrome
extension and a Linux companion. These are documented implementation claims, not a fresh code audit.
Existing live-provider and device acceptance gaps remain open. See architecture, roadmap and verification.

Retain the stack and evaluate reuse before replacing working code. The principal new work is calendar-first
composition, adaptive planning and daily sync, durable loops, unified commitments, connected source ingestion
and a consistent proposal/approval contract.


Proposed logical services
• Source adapters ingest permitted provider changes and maintain cursors, freshness, source references and
  capabilities.

• Commitment reconciliation proposes extraction/merges with evidence and uncertainty; accepted tasks remain
  authoritative.

• Planning services validate capacity/time constraints deterministically; AI helps clarify and explain.

• Proposal service stores versioned effects, reasons, source snapshots, approval and application results.

• Loop runner evaluates scheduled/event triggers with bounded context and creates reports or proposals.

• Focus coordinator manages sessions and configured device controls; device-local expiry supplies recovery.

• Context builder selects minimal permitted information for coaching; disconnected or excluded sources are
  removed.

Use migrations for new durable relations/indexes. Revisit the current planning JSON aggregate tradeoff before

Execution and consistency
A loop run reads a permission-scoped snapshot, derives findings, reconciles known items, creates deduplicated
output and records delivery. A unique logical trigger key prevents retries from duplicating results. Failed/partial
runs retain source freshness and support bounded retry. Use timezone-aware schedules and a documented DST
policy.

Approvals recheck ownership, proposal version, current availability, source versions and destination capability.
Stale input yields a refreshed proposal/conflict. Apply local changes transactionally. Queue external effects
through a durable outbox or equivalent retry-safe design; remote calls cannot be part of the local database
transaction. Unknown provider outcomes require reconciliation before retry. Report partial batch application
honestly; provide recoverable next steps rather than claiming atomic cross-provider writes.

Imported content is untrusted evidence. Structured AI output is validated and cannot execute tools or grant
approval. Preserve current calendar sharing restrictions until a separate reviewed consent change exists.
